# safe-feature-plan

新機能や比較的大きな変更を安全に進めるために、実装に着手する前の「計画」だけを作るSkill。

## このSkillの境界(最重要)

このSkillは調査と計画作成専用。以下は行わない。

- ファイルの編集・作成(Edit/Write)
- パッケージのインストール(npm installなど)
- git commit / push
- デプロイ

計画を提示したら、そこで終了する。ユーザーが計画内で「実装して」「これで進めて」と言ってきても、このSkillの中では実装しない。理由はシンプルで、実装計画をまだユーザーが確認・承認していない段階でコードを書き始めると、想定外の変更が積み重なってしまい、初心者ほど後から差分を追いきれなくなるため。実装は計画提示後、ユーザーが内容を確認し改めて依頼した通常のClaude Codeのやり取りの中で行う。計画提示後に自動で実装フェーズへ進まないこと。

調査のために読み取り系ツール(Read/Grep/Glob/Bashでの`ls`や`cat`相当の閲覧など)を使うのは問題ない。ファイルを変更するツールは使わない。

## 進め方

1. **依頼内容の確認**
   何を実現したいかを整理する。曖昧な場合はコードを読む前に確認する。

2. **現在のプロジェクト構成を調査する**
   関連するディレクトリ・ファイルを読み取り専用で確認し、機能がどこにどう組み込まれそうかを把握する。

3. **変更予定ファイルを洗い出す**
   新規作成が必要なファイル、編集が必要な既存ファイルをリストにする。

4. **既存機能への影響を確認する**
   共有コンポーネント、共通の設定ファイル、他のページ/機能への波及がないか確認する。

5. **新規パッケージの要否を確認する**
   `package.json`を確認し、既存の依存関係で実現できないかをまず検討する。新規パッケージが必要な場合のみ、パッケージ名と「なぜ必要か」を明記する(プロジェクトのCLAUDE.mdにある「追加前に必要性を説明する」ルールに合わせる)。

6. **セキュリティ上の注意点を確認する**
   ユーザー入力の検証、認証・認可が必要か、外部に新しく公開されるエンドポイントがないかなどを確認する。

7. **.env / APIキーの関与を確認する**
   機能の実現に秘密情報が必要か確認する。必要な場合でも、値そのものは書かず、「環境変数名」と設定方法(例: `.env.local`に`XXX_API_KEY`を追加する)だけを計画に記す。

8. **データベース変更の有無を確認する**
   スキーマ変更やマイグレーションが必要か確認する。現状このプロジェクトにDBはないが、将来追加された場合に備えて必ずこの項目をチェックする。

9. **破壊的操作の有無を確認する**
   データ削除、既存ファイルの上書き、force系のGit操作などが計画に含まれていないか確認する。含まれる場合は特にはっきり明記する。

10. **実装後の検証方法を決める**
    変更内容に応じて、lint / 型チェック / test / buildのうちどれを実行すべきかを決める。

11. **Gitコミット単位を提案する**
    どの粒度でコミットを分けるのが安全か提案する(実行はしない、あくまで提案)。

## 出力フォーマット

必ず次の見出し構成のMarkdownで計画を提示する。該当なしの項目も「なし」と明記し、省略しない。

```
# 実装計画: [機能名]

## 概要

## 現在の関連構成

## 変更予定ファイル

## 既存機能への影響

## 新規パッケージ

## セキュリティ上の注意点

## .env / APIキーの関与

## データベース変更

## 破壊的操作の有無

## 実装後に行う検証

## 推奨コミット単位

---
この計画の実装を進めますか?進める場合は改めて依頼してください。(このSkillでは実装は行いません)
```
