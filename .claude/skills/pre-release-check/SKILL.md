# pre-release-check

commit / push / deploy の直前に、変更内容を人間の代わりに一通り点検し、「今リリースして安全か」を報告するSkill。

## このSkillの境界(最重要)

このSkillは点検と報告専用。以下は絶対に行わない。

- ファイルの編集・作成(Edit/Write)
- npmパッケージの追加・削除
- git commit / git push
- デプロイ操作
- 発見した問題の自動修正(**修正案の提示のみ**。実際に直すかはユーザーが判断する)
- 秘密情報の値そのものをチャットに出力すること(ファイル名・行番号・種類だけを報告し、値は絶対に貼らない)

調査のために読み取り系のコマンド(`git status`、`git diff`、lintやbuildの実行など)を使うのは問題ない。ファイルを変更するツールは使わない。

外部通信(外部APIへの疎通確認、デプロイ先サービスの状態確認、外部の脆弱性データベースへの問い合わせなど)を伴うチェックが必要だと判断した場合は、絶対に無断で実行しない。「なぜそのチェックが必要か」を説明したうえでユーザーに確認を取り、許可が出てから実行する。断られた・返事がない場合はそのチェックをスキップし、結果にその旨を明記する。理由:意図しない外部への通信は、それ自体が情報漏洩や誤操作のリスクになり得るため、必ず人間の判断を挟む。

## 進め方

### ステップ0: 変更の有無を確認する(最初に必ず行う)

まず `git status` を実行する。リリース対象となる変更(未commitの変更、または直近の作業で生まれた変更)が無い場合は、それ以降のチェックを無理に続けず、「リリース対象の変更がないため、チェック不要です」という趣旨を簡潔に報告して終了する。空の変更に対して大掛かりなチェックリストを流すのは、ユーザーの時間を無駄にするだけでなく、「何かチェックした感」だけを演出してしまい本末転倒なため。

変更がある場合のみ、以下のステップ1〜12に進む。

### ステップ1: 変更内容の把握

- `git status` で変更・未追跡ファイルの一覧を確認する
- `git diff`(unstaged)と `git diff --staged`(staged)の両方を確認する

### ステップ2: 意図しない変更がないかの確認

直近の会話でユーザーが依頼した内容と、実際の差分を突き合わせる。依頼範囲外のファイルが変更されていないか、削除されているべきでないコードが消えていないかを確認する。

### ステップ3: 不要コード・デバッグコードの確認

`console.log`、`debugger`、コメントアウトされたコードの塊、一時的なテスト用のハードコード値、`TODO`/`FIXME`の残存などがないか差分を読んで確認する。

### ステップ4: lint / typecheck / test / build

変更内容に応じて必要なものだけを実行する(例: UIの文言変更だけならlintとbuildで十分、ロジックを触っていれば型チェックも必須、など)。結果はそのまま報告し、失敗を成功として扱わない。

### ステップ5: エラー・警告の確認

ステップ4の出力に警告(warning)が残っていないか確認する。

### ステップ6: 秘密情報の混入チェック

- `.env`系ファイルがGit管理対象・差分に含まれていないか
- 差分中にAPIキー・トークン・パスワードらしき文字列がないか

検出した場合は、種類と場所(ファイル名・行番号)のみを報告し、値そのものは絶対に出力しない。

### ステップ7: セキュリティ上の懸念

入力値検証の漏れ、認証・認可の不備、XSS・SQLインジェクションなど典型的な問題がないか、差分を目視で確認する。

### ステップ8: 依存パッケージの変更確認

`package.json` / `package-lock.json` の差分を確認し、意図しない追加・削除・バージョン変更がないか確認する。

### ステップ9: DB・外部サービスへの破壊的変更の確認

マイグレーション、DELETE/DROP相当の操作、外部APIへの破壊的な呼び出しなどが含まれていないか確認する。

### ステップ10: 本番公開に影響する設定変更の確認

`next.config.ts`、環境変数関連ファイル、デプロイ設定ファイルなどに変更がないか確認する。

### ステップ11: 未解決の問題・確認事項の洗い出し

会話の中で「後で直す」「保留」とされた事項が残っていないか確認する。

### ステップ12: 外部通信を伴うチェックの要否判断

チェックの過程で外部通信が必要だと判断した場合は、上記「このSkillの境界」の通り、実行前に必ずユーザーに理由を説明して確認を取る。

## 出力フォーマット

変更がある場合、必ず次の見出し構成のMarkdownで報告する。該当なしの項目も「問題なし」「該当なし」と明記し、省略しない。

```
# リリース前チェック結果

## 変更ファイル一覧

## 意図しない変更

## 不要コード・デバッグコード

## lint / typecheck / test / build 結果

## 秘密情報チェック

## セキュリティ上の懸念

## 依存パッケージの変更

## DB・外部サービスへの破壊的変更

## 本番設定への影響

## 外部通信を伴うチェック(実施有無・理由)

## 未解決の問題・確認事項

## 修正案(問題があった場合。実施はしません)

---
## 総合判定: 【リリース可能 / 要確認 / リリース停止】
判定理由:
```

ステップ0で変更なしと判断した場合は、この定型フォーマット全体を出力せず、変更がないことを簡潔に報告するだけでよい。

## 判定基準

- **リリース可能**: 上記チェックすべてで問題なし。lint/typecheck/buildなども成功している。
- **要確認**: 致命的ではないが、ユーザー自身の判断が必要な点がある(例: 未解決のTODOが残っている、意図が読み取りにくい変更がある)。
- **リリース停止**: 秘密情報の混入、lint/typecheck/buildの失敗、破壊的操作、明らかなセキュリティ問題など、明確にブロックすべき問題がある。

## 説明の仕方

このプロジェクトは初心者にも分かりやすい報告を求めている。専門用語(CSRF、マイグレーション、など)を使う場合は一言で構わないので簡単な補足を添える。「〜だから安全です/危険です」のように、判断の理由を平易な言葉で伝えることを意識する。
